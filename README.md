# سامانه تخصیص دانشجو-منتور (نسخه معماری مدولار)

> **منبع حقیقت قوانین تخصیص (LAW v3.0 / Technical SSoT v3.0):** این مخزن باید قوانین ثابت (۶ کلید join، رتبه‌بندی RANK-CORE بر اساس ظرفیت باقی‌مانده، انواع منتور/دانش‌آموز، گیت ظرفیت، trace) را فقط از `docs/LAW_Smart_Student_Allocation_v3.0.md` و `docs/Technical_SSoT_Smart_Student_Allocation_v3.0-TECH.md` بگیرد. این README راهنمای اجراست؛ هر تعارض با LAW/TECH یا روایت‌های قدیمی (مانند occupancy_ratio) LEGACY محسوب می‌شود.

## اجرا
```bash
uv sync --locked
uv run --locked python -m app.main
```

## نسخه‌های شخصی تأییدشده با Git و uv

مسیر معمول Owner پس از انتشار رسمی، یک Git clone اولیه و سپس دریافت نسخهٔ مشخص با Git و هماهنگ‌سازی محیط با `uv` است؛ دانلود مجدد ZIP کامل سورس در هر نوبت لازم نیست. نسخهٔ قبلی در worktree مستقل باقی می‌ماند و انتخاب نسخه خودکار نیست. **`v0.1.0` هدف آماده‌شدهٔ اولین Release شخصی است**؛ انتشار آن تنها با Workflow دستی Owner، نسخه و SHA دقیق `main` پس از Merge انجام می‌شود. راهنما: [انتشار شخصی، فعال‌سازی و rollback](docs/PERSONAL_RELEASE_GIT_UV.fa.md). در CMD از `Matrix-Personal.cmd` استفاده کنید.

## مسیر تحویل پشتیبانی‌شده

مسیر فعلی اجرای Matrix، **سورس پروژه با `uv`** و فرمان‌های بخش «اجرا» است. برای راه‌اندازی از یک پوشهٔ کامل سورس (شامل `pyproject.toml`، `uv.lock`، `.python-version` و منابع پروژه) استفاده کنید؛ این متن ادعای انتشار یک بستهٔ آماده نیست.

ساخت فایل مستقل با PyInstaller، بستهٔ EXE و نصب‌کننده **جزو اهداف تحویل پشتیبانی‌شدهٔ Matrix نیستند**. وجود وابستگی‌ها یا ابزارهای بسته‌بندی تاریخی در مخزن به معنی توصیه یا پشتیبانی از آن مسیر نیست.

## انتشار دستی GitHub Release

مسیر موجود `Owner-controlled GitHub Release` از `Actions → Run workflow` و فقط با تأیید صریح Owner اجرا می‌شود؛ PR یا CI به‌تنهایی Tag/Release نمی‌سازد. GitHub ZIP/TAR رسمی از Git tree ساخته می‌شود و **۳۰ فایل داده‌مانند بررسی‌نشده** با قواعد دقیق `export-ignore` از آرشیو کنار گذاشته شده‌اند، درحالی‌که فایل‌ها در Git checkout و تست‌های Golden باقی می‌مانند. پنج CSV کوچکِ مصنوعی/سرستونی با شناسهٔ دقیق Git مجاز شده‌اند؛ کنترل واقعی ZIP/TAR با همان Commit و اسکن اعتبارنامه‌ها پیش از انتشار الزامی است. این سیاست **تاریخچه و فایل‌های موجود در مخزن عمومی Git را پاک نمی‌کند**. مجوز Vazirmatn/OFL در `THIRD_PARTY_NOTICES.md` ثبت شده و PySide6/Qt از طریق `uv` جداگانه نصب می‌شود؛ حقوق واقعی اشخاص ثالث همچنان محترم است. راهنما: [انتشار شخصی با Git و uv](docs/PERSONAL_RELEASE_GIT_UV.fa.md).

## آماده‌سازی و ارزیابی نسخهٔ منبع با uv

- آرشیو منبع منتخب + نصب `uv` + اجرای دو فرمان بالا در ویندوز، مسیر **کاندیدا/بازیابی** است؛ برای استفادهٔ شخصی نسخه‌دار، مسیر Git+uv روش معمول است. نسخهٔ `0.1.0` در `pyproject.toml` و `uv.lock` به‌عنوان **اولین هدف انتشار شخصی** آماده شده؛ صرف وجود متادیتا به‌معنی ساخته‌شدن Tag/Release نیست.
- Workflow `CI — Windows uv source qualification` در هر PR، تست تکراری پایداری Qt را روی SHA همان PR اجرا می‌کند. همچنین یک ZIP محدود به فایل‌های لازم از Git tree می‌سازد، تمام Blobها و SHA-256 را بررسی و آن را به یک Windows runner تمیز تحویل می‌دهد.
- خروجی قابل‌دریافت `matrix-uv-source-candidate` شامل ZIP و `candidate-manifest.json` است. فایل‌های Excel ریشهٔ مخزن و رکوردهای ورودی فردی همراه Candidate بسته‌بندی نمی‌شوند؛ بااین‌حال، نام مدیران مراکزِ موجود در `config/policy.json`، `policy.yaml` و `policy_sample.yaml` طبق تصمیم صریح Owner برای افشای عمومی تأیید شده‌اند. این مجوز فقط همین نام‌ها را پوشش می‌دهد و جایگزین بازبینی سایر محتویات آرشیو یا مجوز انتشار رسمی Matrix نیست. تست‌های مصنوعی انتخاب‌شده برای بررسی ساخت ماتریس، تخصیص و خروجی Excel همراه Candidate هستند.
- بعد از دانلود، ابتدا `source_sha` و `archive_sha256` مانیفست را با commit بازبینی‌شده و فایل ZIP کنترل کنید؛ سپس ZIP را در پوشهٔ جدید باز کرده و `uv sync --locked` و `uv run --locked python -m app.main` را اجرا کنید.
- **انتشار کنترل‌شده:** قبولی CI یا Merge، خودش انتشار نیست. پس از ادغام PR و تأیید SHA دقیق `main`، Owner اجرای دستی Workflow موجود را با `version=0.1.0` و تأییدهای انتشار آغاز می‌کند؛ همان اجرا اجازهٔ نهایی انتشار است و قبل از آن کنترل منبع، حقوق و محرمانگی دوباره انجام می‌شود. Tag و Release پس از ایجاد، با دانلود واقعی آرشیو و نسخهٔ نصب‌شده بررسی می‌شوند.
- **محدودیت شواهد:** تست‌های Windows CI با `QT_QPA_PLATFORM=offscreen` اجرا می‌شوند؛ تعامل واقعی با نمایشگر فیزیکی، File Dialog و پذیرش اپراتور را اثبات نمی‌کنند.

## تهیهٔ مجاز Profile و قالب Sabt در مسیر GUI

نسخهٔ تمیز سورس uv فایل خصوصیِ تاریخیِ `docs/Report (4).xlsx` را شامل نمی‌شود. پیش از Allocate، فایل **Sabt Export Profile** سازمانیِ مجاز با شیت `Sheet1` و نگاشت ستون‌ها را روی دستگاه اپراتور تهیه و در بخش «خروجی Sabt»، فیلد «فایل پروفایل Sabt» انتخاب کنید. این فایل **الزامی** و متفاوت از `sabt_template` اختیاری است. آن را در Git، آرشیو عمومی یا شواهد CI بارگذاری نکنید. پس از انتخاب ورودی دانش‌آموزان و ماتریسِ Build، مقصد تخصیص و در صورت نیاز مقصد خروجی Sabt را تعیین کنید؛ اگر Template خالی باشد، GUI یک Template حداقلی را در پوشه خروجی ایجاد می‌کند. فایل‌های QA و Sheet2 را با Excel کنترل کنید؛ آزمایش با Profile مصنوعی اثبات سازگاری با سامانه واقعی Sabt نیست.

## Policy-First در Core

- تمامی نام ستون‌ها، مراحل Trace و فیلترها از فایل `config/policy.json` خوانده می‌شوند.
- کلاس `PolicyAdapter` در `app/core/policy_adapter.py` تنها نقطهٔ دسترسی به تنظیمات Policy است.
- برای تغییر رفتار فیلترها، تنها کافی است JSON را ویرایش کنید؛ نیازی به تغییر کد نیست.
- ستون ظرفیت از مرحلهٔ `capacity_gate` گرفته می‌شود و برای Override می‌توان پارامتر صریح به تابع تخصیص داد.

## نرمال‌سازی ورودی

## تست‌های سیاست‌محور

- `uv run --locked pytest -q` سناریوهای ترجیح «کدرشته» بر نام گروه و مصرف ستون ظرفیت از Policy را پوشش می‌دهد.
- تغییر JSON (مثلاً تغییر نام ستون ظرفیت) باید بدون تغییر کد باعث تغییر رفتار تخصیص شود.

## 🏢 مدیریت مراکز

سیستم از مدیریت پیشرفته مراکز پشتیبانی می‌کند که به شما امکان می‌دهد مراکز مختلف را تعریف کرده و برای هر مرکز مدیران مشخصی تعیین کنید.

### پیکربندی مراکز

مراکز در فایل `policy.yaml` تعریف می‌شوند:

```yaml
center_management:
  enabled: true
  default_center_for_invalid: 0
  strict_manager_validation: false
  school_student_column: "is_school_student"
  
  centers:
    - id: 1
      name: "گلستان"
      default_manager: "شهدخت کشاورز"
      description: "مرکز گلستان"
      
    - id: 2  
      name: "صدرا"
      default_manager: "آیناز هوشمند" 
      description: "مرکز صدرا"
      
    - id: 0
      name: "مرکزی"
      default_manager: null
      description: "مرکز اصلی"
  
  priority_order: [1, 2, 0]
```

### استفاده از طریق UI

1. در تب "تخصیص"، بخش "مدیریت مراکز" را پیدا کنید
2. برای هر مرکز، مدیر مورد نظر را از dropdown انتخاب کنید
3. از دکمه‌های زیر استفاده کنید:
   - **بازنشانی به پیش‌فرض**: بازگشت به مقادیر Policy
   - **بارگذاری مجدد مدیران**: به‌روزرسانی لیست مدیران از فایل استخر

> **نکته درباره فناوری UI:** رابط کاربری روی **PySide6/Qt** پیاده‌سازی شده و در حال حاضر هیچ لایه‌ی سازگاری یا Bridge با Tkinter ندارد؛ برای استفاده از Tkinter باید یک Adapter جدید نوشته شود یا از CLI بهره بگیرید.

> **جایگزین‌های پیشنهادی برای UI:**
> - **CLI موجود**: برای خودکارسازی و اسکریپت‌نویسی بدون نیاز به GUI (مسیر کم‌ریسک برای نگهداشت Policy).
> - **Tkinter سبک**: یک entry point جدید بسازید که رویدادهای Tkinter را به همان دستورات CLI نگاشت کند تا از منطق هسته جدا بماند.
> - **TUI/متنی (مثلاً Textual/Rich)**: رابط ترمینالی با کنترل ورودی‌های Policy محور؛ وابستگی گرافیکی ندارد و برای استقرار روی سرور مناسب است.
> - **وب‌اپ کوچک (FastAPI/Flask + HTMX)**: اگر نیاز به چند کاربر یا اجرا در مرورگر دارید، می‌توان از API موجود بهره گرفت و لایه ارائه را وبی کرد.

### استفاده از طریق CLI

```bash
# تنظیم مدیران برای مراکز مختلف
uv run --locked python -m app.cli allocate \
  --center-manager 1="شهدخت کشاورز" \
  --center-manager 2="آیناز هوشمند" \
  --center-priority 1,2,0

# فعال‌سازی validation سخت‌گیرانه
uv run --locked python -m app.cli allocate \
  --center-manager 1="مدیر گلستان" \
  --strict-manager-validation
```

### نسخهٔ برنامه و چرخهٔ کنترل‌شدهٔ انتشار سورس

- **منبع یگانهٔ نسخهٔ برنامه**: فیلد `project.version` در `pyproject.toml`. اجرای `app.main` نسخه را از متادیتای بستهٔ نصب‌شده می‌خواند. سازندهٔ کاندید، برابر بودن نسخهٔ پروژه در `uv.lock` و الزام Python را کنترل می‌کند؛ تست ویندوز نیز نسخهٔ نصب‌شده را با مانیفست تطبیق می‌دهد. نسخه‌های LAW، Policy، schema و Technical SSoT مستقل هستند.
- `0.1.0` **هدف نسخهٔ نخست شخصی** و منبع نسخه در `pyproject.toml` و `uv.lock` است؛ شمارهٔ رسمی تنها با Tag/Release دقیق و تأییدشدهٔ GitHub محقق می‌شود. بخش تاریخی `1.0.0` در Changelog سند انتشار رسمی نیست.

**Prepare → Qualify (بدون انتشار):** از شاخهٔ قابل‌بررسی، PR به `main` بسازید. CI در همان SHA سورس ZIP، `candidate-manifest.json` و آزمایش‌های Windows را ایجاد می‌کند. `source_sha`، `candidate_identity`، `archive_sha256`، `uv_lock_sha256`، فهرست `archive_files`، نتیجهٔ تست‌ها و `privacy_status` را بازبینی کنید. کاندید از فایل‌های Git *همان commit* استخراج می‌شود؛ فایل‌های Excel، Golden و فایل‌های محلی وارد ZIP نمی‌شوند. چند الگوی معتبر و شناخته‌شدهٔ کلید خصوصی/توکن نیز در محتوای آرشیو مسدود می‌شوند؛ این بررسی محدود جای ممیزی کامل محرمانگی را نمی‌گیرد. تصمیم محرمانگی مربوط به **نام مدیران مراکز موجود** در `config/policy.json` / `policy.yaml` / `policy_sample.yaml` با تأیید صریح Owner حل شده است؛ این تصمیم شامل رکوردهای خصوصی، اطلاعات دانش‌آموزان، اسرار یا سایر محتوای احتمالی آرشیو نیست. وضعیت `REVIEW_REQUIRED_BEFORE_PUBLICATION` برای بازبینی کلی آرشیو پابرجاست و هرگز معادل مجوز انتشار نیست.

**انتشار فقط با اجرای دستی Owner روی SHA دقیق:** برای نسخهٔ نخست `v0.1.0`، تغییر نسخه یا PR دیگری لازم نیست مگر شواهد جدید آن را ایجاب کند. بعد از Merge، SHA کامل جدید `main` و موفقیت CI را تأیید کنید؛ سپس در `Actions → Owner-controlled GitHub Release` با `version=0.1.0`، همان SHA و عبارات تأیید مشخص‌شده در [راهنمای انتشار](docs/PERSONAL_RELEASE_GIT_UV.fa.md) اجرا کنید. Workflow باید پیش از ساخت Tag نسخه/lock/CHANGELOG، محتوا و حقوق آرشیو را بررسی کرده و پس از انتشار هویت Tag و فایل‌های میزبانی‌شده را تطبیق دهد. Push/PR/CI خودکار Tag یا Release نمی‌سازد.

**Verify → Recover:** نسخهٔ Tag، SHA، هش ZIP و `uv.lock` را با مانیفست و فایل منتشرشده تطبیق دهید، در Windows تمیز `uv sync --locked` و `uv run --locked python -m app.main` را اجرا و خروجی مصنوعی Build/Allocate/QA/Sabt را کنترل کنید. در انتشار ناقص، لینک‌ها/دانلودها را از معرفی عملیاتی خارج و علت را اعلام کنید؛ پس از رفع مشکل، نسخهٔ اصلاحی جدید با SHA و نسخهٔ تازه بسازید. تاریخچهٔ Tag/Release منتشرشده را بازنویسی یا جایگزین نکنید. سازگاری واقعی Profile سازمانی، دیالوگ/کیبورد فیزیکی ویندوز و پذیرش اپراتور تا مشاهدهٔ مستقل **NOT_PROVEN** هستند.
