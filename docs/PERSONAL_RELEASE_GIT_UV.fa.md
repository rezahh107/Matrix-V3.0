# راهنمای انتشار شخصی Matrix با Git و uv

این مسیر فقط برای استفادهٔ شخصی Owner روی Windows است. عمومی بودن مخزن به معنی انتشار نسخهٔ رسمی نیست. **نسخهٔ `v0.1.0` در ۲۰۲۶-۱۱-۰۷ به‌عنوان GitHub Release رسمی منتشر شده است (سورس `36817ca03bc798fafc091a7bfa7afde22bc7ad76`). نسخهٔ `v0.2.0` فعلاً فقط کاندیداست و انتشار جدید نیازمند تأیید مستقل Owner است.**

## مدل عملیات

یک Git clone ثابت نقش کنترل‌کننده را دارد؛ هر تگ رسمی با Git worktree در پوشهٔ مجزای .matrix-personal/versions/ نصب می‌شود. Git فقط تغییرات/اشیای مورد نیاز را fetch می‌کند؛ بنابراین هر بار ZIP کامل سورس دانلود نمی‌شود، اما worktree یک نسخهٔ کامل محلی است. محیط .venv مستقل هر نسخه ممکن است برای وابستگی جدید دانلود داشته باشد. .matrix-personal/state.json فقط بعد از تأیید tag/pyproject/uv.lock/CHANGELOG، uv sync --locked و import probe به‌صورت اتمی تغییر می‌کند. نسخهٔ قبلی خودکار حذف نمی‌شود.

## آماده‌سازی یک نسخهٔ کاندیدا، بدون انتشار

1. در PR بررسی‌شدنی، نسخهٔ پیشنهادی را در pyproject.toml تعیین کنید؛ uv lock را به‌روز کنید؛ در CHANGELOG.md بخش ## [X.Y.Z] - YYYY-MM-DD و توضیح کوتاه تغییرات اضافه کنید. این اقدام پیشنهاد نسخه است و انتشار نیست.
2. CI برای همان SHA: Windows Core/UI، Windows uv source qualification، LAW/SSoT و Golden مرتبط. اجرای دستی اختیاری: python tools/ci/qualify_uv_source.py --require-release-version X.Y.Z --output-dir OUTPUT_FRESH. خروجی فقط candidate است، نه یک Release.
3. نخستین نسخهٔ `v0.1.0` در ۲۰۲۶-۱۱-۰۷ منتشر شد. برای کاندیدای بعدی (`v0.2.0`)، یک Draft PR و تست‌های همان SHA آماده می‌شوند؛ این PR و تگ آزمایشی محلیِ CI هیچ‌کدام GitHub Release نیستند. نسخه و SHA انتشار آینده تنها هنگام تأیید جداگانهٔ Owner تعیین می‌شوند. CI/PR/Merge انتشار خودکار ندارند.
4. در هنگام انتشارِ مجاز، tag/Source SHA، uv.lock، changelog، CI و آرتیفکت واقعی تطبیق داده شوند. تگ منتشرشده بازنویسی نشود؛ اصلاح با نسخهٔ جدید صورت گیرد.

## GitHub Release با انتشار دستی Owner — قابلیت موجود

**انتشار آینده در PR کاندیدا انجام نمی‌شود؛ `v0.1.0` قبلاً منتشر شده است.** Workflow موجود `Owner-controlled GitHub Release` فقط با `Actions → Run workflow` روی `main` فعال می‌شود؛ Push، PR، Merge، Tag و موفقیت CI به‌تنهایی انتشار را آغاز نمی‌کنند. ورودی نسخه، SHA و عبارت تأیید در اجرای دستی توسط Owner، اجازهٔ نهایی انتشار همان نسخه است.

۱. در PR نسخهٔ موردنظر را در `pyproject.toml` و `uv.lock` یکسان کنید؛ `.python-version` و بخش تاریخ‌دار `CHANGELOG.md` را تطبیق دهید. متن کاندیدای اولیه در `CHANGELOG.md` با توضیح دقیق نسخهٔ آماده‌شده جایگزین شده است؛ نخستین هدف `v0.1.0` بود و Release آن منتشر شده است. بازبینی نسخه و Source SHA دقیق پس از ادغام همچنان لازم است.

۲. بعد از Merge، **SHA دقیق main جدید** را بگیرید؛ SHA قبلی PR با Commit ادغام‌شده ممکن است متفاوت باشد. اجرای دستی فقط با همان SHA فعلی `main` پذیرفته می‌شود. Workflow دوباره مسیرهای موجود Windows uv، Core/UI و Golden را روی همان commit اجرا می‌کند؛ ادعای جایگزینی تست واقعی روی دستگاه اپراتور ندارد. بررسی LAW/SSoT پیش از ادغام نیز باید سبز باشد.

۳. قبل از انتشار، هر دو سطح عمومی را جداگانه بررسی کنید: **GitHub Source code (ZIP/TAR.GZ)** خودکار، که از Git tree تگ ساخته می‌شود اما مسیرهای دقیق `export-ignore` را حذف می‌کند، و **ZIP انتخابی uv + مانیفست**، که فقط فایل‌های مجاز سازندهٔ موجود را دارد. در وضعیت فعلی فایل‌هایی مانند `0918.xlsx` و فایل‌های Excel/CSV در Golden/tests داخل تاریخچه/درخت Git وجود دارند؛ ماهیت برخی از آن‌ها برای افشای عمومی اثبات نشده است؛ فایل‌های بررسی‌نشده فقط از آرشیو عمومی کنار گذاشته می‌شوند و در Checkout برای تست باقی می‌مانند. پنج CSV مصنوعی/سرستونی با Blob SHA دقیق مجاز شده‌اند؛ تغییر محتوایشان دوباره مسدود می‌شود. آرشیو ZIP/TAR واقعی با فایل‌های مجاز Git مقایسه می‌شود. حذف از آرشیو، تاریخچهٔ عمومی Git یا Checkout شخصی را پاک نمی‌کند. تأیید قبلی Owner برای **اسامی مدیران مراکز موجود** معتبر است، اما به دانش‌آموزان، Sabt، اسرار یا دیگر داده‌ها تعمیم داده نمی‌شود. امن‌بودن **آرشیو GitHub** باید مستقل از ZIP انتخابی اثبات شود؛ این کنترل پیش از هر Tag اجرا می‌شود. عمومی بودن قبلی تاریخچه نیز با پاک‌کردن فایل از Commit بعدی پاک نمی‌شود.

۴. حقوق و مجوزها: Owner اختیار دارایی‌های متعلق به خود و انتخاب انتشار شخصی را تأیید کرده است. فونت تعبیه‌شدهٔ Vazirmatn با انتساب و مجوز OFL در `THIRD_PARTY_NOTICES.md` و فایل مجوز همراه سورس پوشش داده شده است؛ Qt/PySide6 در مسیر Git+uv جداگانه نصب می‌شود، نه اینکه باینری Qt همراه ZIP سورس توزیع شود. متادیتای `MIT` به‌تنهایی حقوق کد یا دارایی‌های احتمالی اشخاص ثالث را ایجاد نمی‌کند؛ اگر چنین محتوای مشخصی کشف شد، باید قبل از انتشار همان مورد حل شود. کنترل مخفی‌نماندن مسیرهای ناشناخته، امضای اعتبارنامه‌ها و تطبیق ZIP/TAR فعال است. نبود سند عمومی اضافی برای مالکیت دارایی‌های خود Owner، مانع مستقل انتشار شخصی نیست.

۵. فقط پس از رفع این موارد و تصمیم صریح Owner، در Actions نسخهٔ `X.Y.Z`، SHA کامل فعلی `main`، عبارت `PUBLISH-vX.Y.Z` و پس از بازبینی واقعی عبارت `PUBLIC-SNAPSHOT-AND-RIGHTS-REVIEWED` را وارد کنید. اجرا باید از حساب `rezahh107` باشد. بخش `publish` به Environment با نام `matrix-public-release` ارجاع می‌دهد: می‌توان در `Settings → Environments` آن را با Required Reviewers و محدودیت `main` محافظت کرد (قابلیت‌های لازم در مخزن عمومی بسته به طرح قابل استفاده‌اند). **نام‌بردن Environment در YAML به‌تنهایی به معنی فعال‌بودن تأیید reviewer نیست**؛ تنظیمات فعلی Environment در این PR تغییر یا تأیید نشده‌اند. سطح دسترسی `contents: write` فقط در Job انتشار و نه در Jobهای بررسی درخواست می‌شود.

۶. Job انتشار ابتدا نبود Tag و Release (از جمله Draft) و برابری `main` با SHA را کنترل می‌کند. پیش از هر Tag، **هر دو ZIP/TAR.GZ رسمی GitHub برای SHA دقیق** را دانلود و همهٔ فایل‌ها را با Git blob مقایسه می‌کند. سپس Tag **annotated** را بدون force دقیقاً روی SHA می‌سازد، هدف واقعی Tag را می‌خواند و **هر دو آرشیو GitHub برای همان Tag** را نیز پیش از انتشار کنترل می‌کند. Release با `--draft --verify-tag` ساخته می‌شود و ZIP انتخابی و `release-provenance.json` به Draft متصل می‌شوند. فقط پس از خواندن Draft از API احراز هویت‌شده، تطبیق کامل نام/وضعیت/اندازه/هش و دانلود واقعی هر دو Asset، بررسی مجدد Tag/`main` و متن Release Notes، **یک بار** تغییر `draft=false` درخواست می‌شود. فیلد `target_commitish` ملاک مالکیت سورس نیست و هدف Tag annotated مستقل از آن تأیید می‌شود. بعد از انتشار نیز آدرس/Tag، Assetها و هر دو آرشیو خودکار GitHub دوباره راستی‌آزمایی می‌شوند. هیچ مسیر انتشار جایگزین یا Installer/EXE اضافه نشده است.

### شکست و بازیابی بدون تخریب

- SHA قدیمی، نسخه/lock/Changelog نامعتبر، فایل یا حقوق عمومی تأییدنشده، CI قرمز، داده/Asset ناسازگار، نبود مجوز و اجرای هم‌زمان: **توقف قبل از انتشار**. Lock سراسری Actions برای هم‌زمانی و خطاهای API برای تعارض استفاده می‌شود؛ موفقیت را از روی Exit Code به‌تنهایی اعلام نکنید.
- اگر Tag ساخته شد ولی پیش‌بررسی آرشیو یا ایجاد Draft شکست خورد، هیچ Tag را پاک یا جابه‌جا نکنید. وضعیت Tag و فهرست Releaseها (حتی Draft) را با مجوز نوشتن/خواندن بررسی کنید. `resume-tag-only` فقط زمانی مجاز است که Tag annotated دقیقاً روی SHA تأییدشده باشد و **هیچ Release یا Draft موجود نباشد**؛ Draft ناقص به‌صورت خودکار تکمیل، حذف یا بازنویسی نمی‌شود.
- اگر Assetهای Draft ناقص/نامعتبر باشند، Draft **منتشر نمی‌شود** و برای بررسی دستی باقی می‌ماند. اگر درخواست تغییر Draft به انتشار قطع شد، نتیجه را «نامشخص» تلقی کنید و بدون تکرار نوشتن، خود Release را با ID بررسی کنید. اگر Release منتشر شد ولی کنترل پس از انتشار شکست خورد، لینک را معرفی نکنید و فقط شواهد را **read-only** بررسی کنید. هیچ بازنویسی Asset، حذف Release، حرکت‌دادن Tag یا تلاش خودکار مجدد انجام نمی‌شود؛ برای اصلاح محتوای منتشرشده معمولاً نسخهٔ تازه لازم است.
- اجرای این workflow یا موفقیت مجموعه تست‌های شبیه‌سازی‌شده، پذیرش Sabt واقعی، GUI فیزیکی، بازگشت schema دیتابیس یا Windows Registry را اثبات نمی‌کند.

## نصب، فعال‌سازی، اجرا و rollback روی Windows

پیش‌نیاز: Git for Windows، uv، اتصال به مخزن و مجوز دسترسی آن. فرمان‌ها در PowerShell یا CMD:

~~~powershell
git clone https://github.com/rezahh107/Matrix-V3.0.git
cd Matrix-V3.0
uv python install 3.11
.\Matrix-Personal.cmd activate vX.Y.Z
.\Matrix-Personal.cmd status
.\Matrix-Personal.cmd start
~~~

در ارتقای بعدی، فقط نسخهٔ رسمی و مصوبِ دقیق را مشخص کنید (هرگز latest به‌صورت خودکار انتخاب نمی‌شود):

~~~powershell
.\Matrix-Personal.cmd activate vA.B.C
.\Matrix-Personal.cmd status
.\Matrix-Personal.cmd start
~~~

اگر نسخهٔ جدید هنگام استفاده نامناسب بود، بعد از بستن Matrix:

~~~powershell
.\Matrix-Personal.cmd rollback
.\Matrix-Personal.cmd start
~~~

عبارت‌های vX.Y.Z و vA.B.C جای‌نگهدارند؛ نسخهٔ فعال فقط با وجود تگ رسمی و قابل‌تأیید در GitHub معتبر است. status نسخه و SHA کامل فعال و قبلی را نشان می‌دهد. activate/rollback برنامه را باز نمی‌کنند. start برنامه را از محیط قفل‌شده همان نسخه با python -m app.main اجرا می‌کند. Launch_Matrix3.cmd برای اجرای checkout اصلی است و معادل انتخاب نسخهٔ تأییدشده نیست.

## آماده‌سازی ارتقای بعدی روی رایانهٔ شخصی

- کاندیدای `v0.2.0` هنوز تگ رسمی ندارد؛ تا انتشار و تأیید مستقل Owner، فرمان `activate v0.2.0` را روی رایانهٔ واقعی اجرا نکنید.
- برای نسخهٔ رسمی، ابتدا Matrix را ببندید، `Matrix-Personal.cmd status` را بررسی کنید و از دیتابیس‌های `%USERPROFILE%\.smart_alloc\years\`، تنظیمات JSON، Registry/QSettings مربوط به Matrix و همهٔ Profileها/خروجی‌های خارجی انتخابی در محل مستقل نسخهٔ پشتیبان بگیرید؛ صحت SQLite را با `PRAGMA integrity_check` و بکاپ‌ها را با بازخوانی داده کنترل کنید.
- پس از انتشار مجاز نسخهٔ بعدی، با `Matrix-Personal.cmd activate vA.B.C` و سپس `status` و `start` نسخهٔ فعال و کارکرد برنامه را کنترل کنید؛ در صورت خطا، قبل از تلاش برای تغییر داده یا حذف worktree عملیات را متوقف کنید.
- `Matrix-Personal.cmd rollback` فقط کد نسخهٔ قبلی را انتخاب می‌کند؛ بازیابی SQLite، تنظیمات Registry و فایل‌های خارجی فرآیندهای مستقل‌اند و سازگاری معکوس Schema نیازمند بررسی است.

## مرز داده و بازیابی

- هنگام ارتقا/rollback برنامه را ببندید. هر تغییر ردیابی‌شده یا فایل untracked در checkout پایه یا worktree فعال باعث توقف عملیات می‌شود. هیچ Git reset --hard، Git clean، حذف خودکار نسخهٔ قبلی یا بازنویسی اطلاعات شخصی انجام نمی‌شود.
- SQLiteهای سالانهٔ GUI در ~/.smart_alloc/years/ و تنظیمات JSON در ~/.smart_alloc/user_settings.json هستند. پیش از فعال‌سازی با SQLite online backup نسخهٔ جداگانهٔ فایل‌های .sqlite و .db آن پوشه برداشته می‌شود؛ شکست بکاپ مانع فعال‌سازی است. بکاپ‌ها داخل .matrix-personal/backups/ هستند و پیش از حذف clone باید به محل مستقل منتقل شوند.
- QSettings در Windows Registry نگهداری می‌شود؛ شناسه‌های Qt مورد استفاده عبارت‌اند از YourOrg/AllocationApp و YourOrganization/MentorAllocation. updater تنظیمات را دستکاری نمی‌کند، ولی بکاپ خودکار Registry انجام نمی‌دهد. پس از اجرای نسخهٔ جدید، اگر فرمت تنظیمات تغییر کند، rollback کد تضمین برگشت تنظیمات نیست.
- خروجی‌های خودکار GUI به‌طور پیش‌فرض در Documents/MentorAllocation/Output قرار می‌گیرند؛ QSettings می‌تواند این مسیر را تغییر دهد. فایل خصوصی Sabt Profile با انتخاب کاربر تعیین می‌شود و ممکن است در هر محلی باشد؛ فایل‌های خارج از مسیر دیتابیسِ شناخته‌شده در بکاپ خودکار پوشش ندارند. آن‌ها را خارج checkout/worktree نگه دارید و جداگانه بکاپ کنید.
- Policyهای پیش‌فرض ردیابی‌شده (config/policy.json، policy.yaml، policy_sample.yaml) به هر نسخه تعلق دارند. ویرایش محلی tracked مانع فعال‌سازی می‌شود؛ اصلاحات سفارشی به نسخهٔ جدید خودکار منتقل نمی‌شوند. از این موارد در یک محل مستقل نسخه بردارید و سازگاری آن‌ها را با LAW/SSoT بررسی کنید.
- کاربری که مسیر Profile/خروجی را به داخل worktree قبلی داده، باید پیش از هر حذف دستی worktree مسیر را بررسی و به محل پایدار منتقل کند. ابزار هیچ نسخهٔ قدیمی را پاک نمی‌کند.
- rollback فقط **کد، tag و uv environment** قبلی را دوباره فعال می‌کند؛ **دیتابیس و Registry را restore نمی‌کند**. پس از اجرای نسخهٔ جدید، سازگاری معکوس schema ممکن است برقرار نباشد؛ بازیابی دیتابیس واقعی نیازمند بررسی و توقف برنامه و تصمیم مستقل است.
- فقط یک عملیات activate، rollback یا start می‌تواند هم‌زمان اجرا شود. تا وقتی برنامه با start باز است، عملیات به‌روزرسانی/rollback دوم رد می‌شود. اگر فرآیند در میانهٔ کار غیرعادی متوقف شود، پوشهٔ `.matrix-personal/.operation-lock` ممکن است باقی بماند. در این حالت **ابتدا همهٔ پنجره‌های Matrix و فرمان‌های فعال Git/uv را بررسی و متوقف کنید**، سپس فقط همین پوشهٔ قفل را به‌شکل دستی حذف و دوباره status را اجرا کنید؛ ابزار عمداً قفل مشکوک را خودکار پاک نمی‌کند.
- شکست fetch، tag، تطبیق نسخه، Python، uv sync، import یا snapshot وضعیت فعال قبلی را حفظ می‌کند. ممکن است worktree نیمه‌آماده برای بررسی باقی بماند؛ هیچ پاکسازی مخربی انجام ندهید.
- فایل‌های داخل .venv، logs، artifacts و cacheها ممکن است توسط ابزارهای معمول بازتولید/پاک شوند؛ فایل خصوصی را به این مسیرها نسپارید. اعمال چند نسخهٔ هم‌زمان بدون هماهنگی مجاز نیست.

## مرز شواهد

تست مصنوعی Git+uv و Windows CI offscreen معادل پذیرش GUI واقعی و Profile سازمانی Sabt نیست. D1، D2، D3 و D5 همچنان اهداف مستقلی هستند.
